# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository. It stays deliberately thin: only universal orientation lives here. Task-specific depth lives in `workbench/`, pulled in on demand via the hooks below.

## First: is this codebase someone's yet?

**If `PRODUCT.md` doesn't exist, the codebase hasn't been made anyone's yet.** Read `START-HERE.md` and follow it before anything else: it asks about the business, then sets the theme, the copy and the names, and writes `PRODUCT.md` and `DESIGN.md`. Once `PRODUCT.md` exists, `START-HERE.md` has done its job and this section can go.

## Workbench

Task-specific docs live as Markdown files at the top level of `workbench/`. Subfolders hold other kinds of things: helper scripts live in `workbench/scripts/`. **Check this list before starting work — when a hook matches your task, read that doc first.** Match hooks on intent, not keywords. When several hooks match, read all of them.

- **Writing or editing any code** → read `workbench/writing-code.md` first. Where code lives (`source/frontend`, `backend`, `database` and `utilities`, and what may import what), the data and its migrations, local development on the checkout's own Postgres, the conventions biome can't enforce (zod wherever data comes in, type assertions, tagged result types, explicit branches, file structure), and the verification loop.
- **Designing or changing anything a person sees** (a page, a component's look, its layout, motion or copy) → read `PRODUCT.md`, `DESIGN.md` and `workbench/designing.md` first. PRODUCT.md holds who the business serves and how it sounds; DESIGN.md holds the visual system: its colors, type and shapes, as `source/frontend/styles.css` sets them; designing.md holds the habits that make a site look generated, and the checks every page passes.
- **Committing, opening a PR, or shipping anything** → read `workbench/commit-and-deploy.md` first. **`main` only changes through a pull request, and merging one deploys to production.** Work on a branch per task, and push it and open the PR only when you are asked to ship. The commit gate, the push gate, how a deploy reaches Railway, its variables and secrets, domains, and Railway's CDN.
- **Reading or fetching any web page or online docs** → read `workbench/read-webpages.md` first. The Jina Reader one-liner and the HTTP-200-but-empty trap.
- **Updating this codebase from the template it came from** (the owner asks for the latest release, an update, or a fix the template has shipped) → read `workbench/updating.md` first. `.superforge/superforge.json` says which template and release this is. An update applies the template's own diff between two releases, one release at a time, on a branch, after the owner has agreed to what its notes in `CHANGELOG.md` flag, and leaves out the lockfile, the migrations and what only the template has.

### Write in American English

**Everything you write here is American English**: code, comments, docs, UI copy, commit messages. `behavior`, `color`, `canceled`, `organize`, `judgment`, `toward`, `gray`, `catalog`. (If the business writes to its customers in another variety of English, PRODUCT.md says so, and the site's copy follows PRODUCT.md.)

### Write names in full

**Name things with whole words**: variables, functions, files, folders, bindings and scripts. `database`, not `db`; `utilities`, not `utils` or `lib`; `context`, not `ctx`; `error`, not `err`. Exceptions: names a tool or library sets (`vite.config.ts`, `drizzle.config.ts`, React's `props`, shadcn's generated primitives), and acronyms that are the word (`id`, `url`, `api`, `html`).

### Keep things current as you go

There is no separate planning, reporting, or review phase, and no status docs in the repo. Work the task; keep these true as you finish:

1. **This file** — if you add, remove or fundamentally change an area of the repo listed under [Project Architecture](#project-architecture), update the list in the same change.
2. **The READMEs** — if your change affects what a directory's `README.md` describes, update it in the same change.
3. **The PR**, when you were asked for one — say what changed and why, and anything the human has to do around the merge.
4. **The workbench docs** — if one you used is stale or wrong, fix it in place when the fix is small and certain; otherwise tell the human what's wrong.

## Project Architecture

This is **one TanStack Start app, in a single pnpm package**, deployed as one Node server on Railway, on one Postgres. There is no monorepo: the pages and the API ship together, and background work runs in the same server, on DBOS. A part that needs to deploy on its own later becomes a second Railway service in the same project, started from this same package. **It's headless**: every database read and write goes through `backend/`'s operations, which the Hono API under `/api` is how people and agents reach, and workflows call directly; never a page, a loader or a server function (`workbench/writing-code.md`, "Headless").

An `AGENTS.md` at the root points Codex and Cursor here.

- **`source/server.ts`** — Start's server entry, the one Vite builds into `output/server/` with everything it imports: `/api/*` to Hono, everything else to TanStack Start. It exports the workflows' `startWorkflows` and `stopWorkflows`, and a dev server starts them as it first loads it (the build's prerender loads it too, and never does).
- **`source/node.ts`** — the Node server Railway runs (`pnpm start`, after `pnpm build`): the client build's files first, every prerendered page among them, with what browsers and Railway's CDN may cache of each, then the built `server.ts` for everything else. It starts the workflows once it's listening, and stops them on SIGTERM before it finishes its requests. Node runs it from source, so it imports only packages and the build.
- **`source/frontend/`** — the website: TanStack's `router.tsx` (with the query client on its context) and generated `routeTree.gen.ts`, `styles.css` (Tailwind and shadcn's theme tokens, light and dark following the device), `routes/` (one file per page, every public one prerendered, `sign-in.tsx` among them, where customers and staff sign in and the sign-in email's link lands, and `dashboard/`, the screens behind sign-in, drawn in the browser and left out of the prerender: a list beside what's chosen from it, `workflows.tsx` and `people.tsx` for the business's own people and `account.tsx` for everyone, which is all an external person sees), `components/` (in folders by what they're for: shadcn's primitives, on Base UI, in `primitives/`, configured by `components.json` at the root, `states/` for what a screen shows when there's nothing to, like `not-found.tsx`, `site/` for the public pages', like `sign-in-form.tsx` and `business-mark.tsx`, the business's name and logo that the sign-in page and the dashboard share, `dashboard/` for the dashboard's, its frame in `shell.tsx` and a run's steps drawn as a line in `marks.tsx`, and `welcome/`, the template's home page's line map, which START-HERE.md's step 3 deletes with the page) and `queries/` (TanStack Query's options, a file per area of the API, through its typed client, like `health.ts`, `auth.ts`, who's signed in and signing in and out, `account.ts`, `users.ts` and `workflows.ts` for the dashboard, and `failures.ts`, which reads a failure the API answered, and `FailedRequest`, which a mutation throws).
- **`source/backend/`** — the Hono API under `/api`, a folder per feature, each with its `routes.ts`, its operations (the only code that touches the database, a file per verb), its `workflows.ts` if it has background work, and its `tests/`. `index.ts` (`apiWith()`, which mounts each feature's routes and puts the database, the bucket, the workflows, Infra and who can sign in on `context.var`, so a test runs the whole API on a database of its own, with Infra's stand-in, `tests/support/api.ts`, and signs people in with `tests/support/sign-in.ts`), `context.ts`, `failures.ts` (the one shape every route fails in: `failure()`, and `validated()`, which checks a route's input with zod), `health/` (`/api/health`, which Railway's healthcheck calls and which needs the database: the smallest feature), `auth/` (signing in under `/api/auth`: `routes.ts`, which asks Infra to email a code and a link and to check them, `access.ts`, who can sign in (anyone, or only people already listed) and who's internal from their first sign-in, which START-HERE.md sets, `sign-in.ts`, which makes the user at their first sign-in and starts a session, `sessions.ts`, the sessions in `auth.sessions`, and `signed-in.ts`, the `session` cookie and the `signedIn`, `maybeSignedIn` and `internalOnly` middleware, the one place that decides who's signed in, putting the user on `context.var.user`), `account/` (the signed-in person's own, under `/api/account`: their name, and the browsers they're signed in on), `users/` (everyone who can sign in, under `/api/users`, for internal people only: listing, adding someone, changing a role, removing someone; and `workflows.ts`'s `tell-team-of-sign-up`, the template's sample workflow, which a sign-up starts and which tells the internal people, in the logs until Infra can email), `infra/` (Superforge Infra, the backend services the app runs on, through the one wrapper on `context.var.infra`: `answers.ts`, what Infra answers, as zod schemas, `client.ts`, over HTTP with a project's key, `stand-in.ts`, Infra's test mode in memory, which the tests and a dev server without a test key use, and `choose.ts`, which takes a secret key in a build and a test key in a dev server, never the other way round; its README has the calls and the keys), `workflows/` (DBOS, for background work, in this process with its runs in Postgres: `define.ts`'s `defineWorkflow`, `index.ts`'s `WORKFLOWS`, every one there is, `queues.ts`, `engine.ts`, which launches DBOS behind an advisory lock, the gate, so the old and new deployments never both run it, starts runs through a DBOS client until it has, prunes finished runs, and reads and retries runs through DBOS's own functions, `runs.ts`, a run as the dashboard shows it, and `routes.ts`, the runs under `/api/workflows` for internal people; its README has the rules every step follows), and `client.ts`, the typed client the frontend calls it with. `frontend/` imports only `client.ts` and types from here.
- **`source/database/`** — Postgres, through Drizzle: `schema.ts` (the source of truth, and its four Postgres schemas: `public` for the business's data, its `users` among it, each with a `role`, `internal` or `external`, which decides what of the dashboard they see, `auth` for what lets someone in, its `sessions`, `internal` for the machinery, and `dbos`, DBOS's own), `migrations/` (drizzle-kit's, applied before each deploy by `migrate.ts`, `pnpm database:migrate`, which then applies DBOS's own), `index.ts` (`connect()` and `appDatabase()`, the server's: `DATABASE_URL`, or this checkout's own in a dev server), `local/` (this checkout's own Postgres, which `pnpm dev`, the tests and the `database:*` scripts use: a Postgres 18 from npm rather than Docker, one per checkout in `.postgres/`, which stops itself once idle for half an hour), `seed/` (the sample rows `pnpm database:seed` writes, like `users.ts`'s users and sessions: every table gets a seeder, or a reason in `UNSEEDED`, which its test checks; it then puts real runs of the sample workflow on the queue, for a dev server to run), `storage/` (the `Storage` bucket, for files: `files.ts`'s `Storage` class has a getter for each kind of file, a folder in the bucket with its key checked by zod, its path and its format (`kind.ts`: zod-checked JSON, text or bytes), as `context.var.storage` in a route, kept through Railway's S3 API in a build and in `.storage/` in a dev server; no kinds yet), and `tests/` (a database of each test's own, the upgrade test, and the bucket's bytes in memory). Server-only.
- **`source/utilities/`** — what both sides share: `primitives/` (what knows nothing of the app, like `durations.ts`) and `schemas/` (the zod schemas both sides check with, a file per feature, like `failures.ts`, the shape every failure takes, `auth.ts`, an email address, a sign-in code and a link's token, and `users.ts`, the roles (`ROLES`, and `INTERNAL_ROLES`, the ones that see the business's side of the dashboard) and what the account and People screens send).
- **`source/globals.d.ts`** — types every file uses without importing them: `OperationResult` and `AsyncOperation`, for expected failures.
- **`public/`** — static files served as-is from the site root, like `favicon.svg`.
- **`.env.example`** — what a checkout's `.env` may set, which git ignores: a dev server's Infra test key (`INFRA_TEST_KEY`), read from the main checkout's `.env` in a worktree with none of its own. Nothing in it is needed to run.
- **`workbench/`** — docs and scripts for working on the repo (above). `scripts/check.sh` is `pnpm check`, whose two parts, `code` and `tests`, it runs side by side as CI does; `check-migrations.sh` and `upgrade-test.sh` check the migrations; `smoke-test.mjs` runs the build as Railway does and probes it, its workflows' launch among it; `seed.mjs` runs the seed.
- **`.github/workflows/ci.yml`** — CI: `code` (with the smoke test) and the tests in two shards, side by side, behind the `check` gate, on every PR and push to `main`; then on a push, `railway config apply`, the one job with production's Railway token, which skips with a notice until a copy has set it. Railway deploys each push to `main` itself, once this whole run passes. `dependabot.yml` opens a PR a month for what's out of date.
- **`.railway/`** — the Railway project as code (`railway.ts`): its region (`REGION`, one choice for everything in it), the app service, its build, pre-deploy migrations, start, healthcheck, CDN and variables, the Postgres database with its point-in-time recovery bucket, `Postgres-PITR` (restoring it is in `workbench/writing-code.md`), and the `Storage` bucket, whose S3 credentials the app gets as `STORAGE_*`, and `INFRA_SECRET_KEY`, the secret key sign-in calls Infra with, which the owner sets in Railway's dashboard. CI applies it; change Railway there, not in the dashboard.
- **`.superforge/`** — what Superforge knows about this codebase, beside the other services' folders (`.claude/`, `.github/`, `.railway/`). For now one file, `superforge.json`: the template it came from (`template`, the template's internal code, which is also its repository's name) and the release it's on (`version`), which an update moves and nothing else edits. It's JSON so a script, an MCP server or the build can read it without running anything.
- **`CHANGELOG.md`** — the template's releases, newest first, each a `v` tag on the template's repository, written for the agent that updates a copy (`workbench/updating.md`). A copy keeps it as its updates leave it.
- **`LICENSE`** — MIT, for the template's code this codebase started from.
- **`START-HERE.md`** — the onboarding that makes this codebase a business's own. `PRODUCT.md` and `DESIGN.md`, which it writes, hold the business and its look.

### Keeping this list current

If you add, remove, rename, or fundamentally change the purpose of an area above, **update the list in the same change.**

## READMEs

Directory-level `README.md` files own the deep context. Read one before changing anything in its directory, keep it current in the same change, and add one only when a directory's context can't be inferred from the code.

## Before Committing, And Before Shipping

**A local commit is a checkpoint**: `pnpm format`, plus `pnpm typecheck` if you touched code.

**A push or a PR runs the full gate:**

```bash
pnpm format && pnpm check
```

`pnpm check` is exactly what CI runs, its parts side by side as CI's jobs run them (biome, the migration check, the typecheck, the tests against Postgres with the upgrade test, the build with its prerender, and the smoke test of the build). The tests start the checkout's own Postgres, which `pnpm install` brought. Merging to `main` deploys to production. Everything else about shipping lives in `workbench/commit-and-deploy.md`.
